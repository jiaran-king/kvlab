# Goal v4：四张 H20 上的 KV 容量、缓存移除与性能响应

## 1. 目标与已有结论

在现有原生 P/D 分离部署上，将工作负载扩大到六个交错 session，保持请求并发为3，仅改变 **P 侧每卡 KV 预算：12／24／48 GiB**。

回答：

1. 是否观察到容量相关的缓存移除？
2. 容量变化是否对应移除、命中率和本地输入计算计数的变化？
3. 这些变化是否体现为 P prefill、后续轮 TTFT 和 E2E 的变化？

旧版174请求实验已经得到三个有效容量点：

| P 每卡 KV 预算本地命中率local compute token |        |         |
| ---------------------------------- | ------ | ------- |
| 12 GiB                             | 89.81% | 710,994 |
| 24 GiB／M2                          | 92.54% | 520,530 |
| 48 GiB／H2                          | 92.54% | 520,530 |

因此，“原负载偏轻”仍是待验证假设。新实验检查扩大工作集后的响应，不要求三档命中率明显分开，不要求24 GiB处于过渡区、48 GiB零驱逐、性能单调或出现正收益。

新负载形成独立实验系列，不能与旧版174请求拼接成容量曲线。

## 3. 工作负载：六个完整 session，请求并发3

从现有 `claude_trace_8session_requests.jsonl` 选择完整 session，核对既有代码及trace来源：
```
7f304555a8bc504c2c2257db2662e896eeeb5c30
```

默认保留原三个 session，再加入三个满足上下文上限、长输入、多轮复用特征的 session。保留原输出长度、actor和子任务依赖，不截断上下文、不强制短输出、不机械重复同一trace。

正式运行前保存 manifest，包含：

- session清单、计划请求数及选择理由；
- 输入／输出长度分布和最长请求；
- 回放参数、上下文续接及reset口径。

合适session不足六个时如实记录，不为凑数量改造trace。

**六个 session 的请求应实际交错，在途请求始终不超过三个。** 复用现有调度逻辑；若限制作用于整个session，导致先跑完三个再启动另外三个，才做最小调整。不得为此开发新的确定性调度框架。

抽查少量实际构造的prompt，确认不同session的主要长前缀存在差异，同一actor后续轮保留预期前缀。允许共享真实公共前缀，不用随机加盐制造独立性。

继续使用闭环回放，不声称固定seed保证不同容量点的请求交错和实际token内容完全一致。

## 4. 新增观测及短检查

### P侧KVEvent

本轮核心新增项是P侧缓存事件采集：
```
BlockStored
BlockRemoved
AllBlocksCleared
```

先核对**冻结安装版本**的事件能力、字段和触发路径，优先复用现成订阅实现。订阅器在预热前就绪，缓冲落盘，避免逐事件同步刷盘或打印长token列表。

统计正式窗口内：

\\[ N\_{\mathrm{removed}} =\sum \operatorname{len}(\text{BlockRemoved.block\\\_hashes}) \\]

口径：

- 统计移除条目数，不是消息条数。
- 同一hash多次存回和移除应重复计数；只去除明确的消息重传。
- 保留实际存在的时间戳、序号、engine、medium、group等字段；多group分开报告。
- 未核实映射关系前，不将条目数换算为物理block、token或字节。
- 只有确认触发路径属于容量相关替换时，才称为“capacity eviction”；否则称“缓存移除条目”。
- 预热和reset事件排除在正式统计外；正式期间全量清空单列异常。
- 检查可用序号、采集错误和结束排空情况；丢事件或采集失败不能记成零移除。

不实现逐block因果追踪，不把 `removed/stored` 当作miss rate。

### 一次必要的观测检查

使用原两条预热检查服务、APC和新增事件链路，不再强制复现M1的旧失败短链。

正式协议保持：
```
订阅器及metrics采集就绪
→ 原两条预热完成
→ 等待请求与传输收尾
→ reset P prefix cache，确认成功
→ 明确事件窗口边界，采 formal-before metrics
→ 完整Replay
→ 等待收尾、采 formal-after metrics、排空事件
```

若核心事件能力缺失、采集不可靠，或必须侵入式修改运行时才能获得，先交付具体能力缺口，**不消耗完整回放预算**。不因缺少辅助指标阻塞实验。

### 辅助观测

每两秒采集现有P/D `/metrics`：

- KV usage、running、waiting：报告采样均值和峰值；
- queue和prefill histogram：使用正式窗口 `Δsum/Δcount`；
- preemption：使用counter增量。

不设置KV usage超过95%的门槛，不用低usage判定没有驱逐。

若当前版本已有KV residency抽样指标，可开启1%采样，记录lifetime、idle-before-evict和reuse-gap；不支持则省略，样本不足则注明，不提高采样率追加实验。

Mooncake传输指标已有则收，没有则注明，不新增完整tracing或profiling。

## 5. 正式运行顺序与预算

**默认顺序：****`12 → 48 → 24 GiB`****，共三次完整回放。**

先运行12和48 GiB两个端点，从开始就完整采集。它们同时承担负载检查和正式对照；完整、可比的运行直接保留，不再重复一套“正式实验”。

默认不调整六-session负载。命中差异小、48 GiB仍有移除、TTFT没有改善，都不是调整理由。

仅当以下条件同时满足时，允许一次扩到现有trace中最多八个合适session：

- 事件采集完整；
- 已确认主要前缀差异和实际交错；
- 两端均未观测到可确认的容量相关移除；
- 剩余预算足够完成调整后三档。

调整后重新测两个端点，再测24 GiB。原六-session结果保留为独立校准材料，不混入新系列。八个session仍无差异就如实报告。

**最多五次完整规模尝试，失败也计入。** 额外两次由负载调整或客观异常补测共享，不叠加预算、不隐式重试、不因结果不理想补跑。

影响可比性的修复必须统一应用于同一对照系列；预算不足时交付有效结果和缺口，不追加次数。

## 6. 核心统计和结果判断

主表保留：

| 类别指标  |                                                      |
| ----- | ---------------------------------------------------- |
| 容量    | P每卡预算、实际blocks、block／group配置                         |
| 请求覆盖  | 计划、成功、失败、超时、依赖跳过                                     |
| 缓存移除  | 分group移除条目数、事件完整性及原因口径                               |
| 本地命中  | P的hit/query增量及token加权命中率                             |
| 输入计算  | P的local\_compute总量和输入占比；local\_cache\_hit、external计数 |
| 阶段时间  | P prefill均值                                          |
| 客户端性能 | 后续轮TTFT P50／P95；首次、独立及reset请求单列                      |

辅助表保留E2E P50／P95、任务窗口、queue、preemption、usage及已有传输指标。

`local_compute`包含首次、新增及未命中输入，不能称为纯重复计算、FLOPs或GPU耗时。命中增加和local\_compute减少可能是同一输入账目的两个方面，不当作独立性能证据。

Counter采用正式窗口差分，不混加P/D或重复TP序列。阶段均值与分位数不能相加减构造TTFT。Queue变化可能是容量变化后的系统响应；preemption非零时，说明结果包含运行中调度效应。

分别判断请求覆盖、事件完整性和时延解释范围。失败运行完整保留，不用成功子集补成有效容量点、不插值、不填零。记录实际编译区间、KV错误及明显背景干扰，不凭普通JIT告警删除结果。

## 7. 改动范围、资源与交付

改动限于：

- KVEvent订阅与缓冲落盘；
- 周期metrics采集；
- 必要的session交错调整；
- 统计汇总和图表。

不开发模拟器、缓存策略、APC-off消融、QPS／并发矩阵、Nsight／MFU分析或新的Replay框架。

遵守H20的SLURM和服务器健康规则。所有服务与采集器必须有明确资源、时间上限和停止条件；启动前及退出后保存必要健康与资源归属证据，清理仅限本轮所属进程、端口和IPC。不得覆盖旧实验或触碰其他作业。

交付目录为 **`stage-v4/`**，保留配置、manifest、代码改动、运行台账、逐请求结果、P/D及Proxy日志、metrics、KVEvent、清理证据、`summary.csv`和`REPORT.md`。

只做四张图：

1. 命中率—容量；
2. local\_compute—容量；
3. 累计移除—完成请求进度，保留group口径；
4. 后续轮TTFT P50／P95—容量。

事件按完成进度对齐仅用于展示，不据此归因到单个请求。失败点明确标注，单次运行不虚构误差条。

**验收目标是取得三个可比容量点及可信的缓存移除观测。预算内无法补齐时，交付已取得的有效结果、失败证据和明确限制；不以漂亮曲线、找到拐点或正收益作为完成条件。**
